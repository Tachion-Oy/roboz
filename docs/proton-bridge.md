# Proton Mail Bridge with Shed email tools

`ProtonBridgeEmailService` implements the Shed `EmailService` contract. It can
search Inbox, Drafts, and Sent; read messages; download attachments; and create
standalone and threaded reply drafts. It cannot send, delete, or move mail. The
existing Shed email factory applies the file permissions for draft attachments
and downloaded files.

Run Proton Mail Bridge where the application can reach its IMAP listener. Use
the IMAP username and password generated by Bridge, not the Proton account
password. Find the host, port, and TLS mode in Bridge's mailbox details.

## Encrypt credentials and construct the service

Only names ending in `_SECRET` are selected for encryption. An example `.env`
is:

```dotenv
PROTON_BRIDGE_USERNAME_SECRET=bridge-user
PROTON_BRIDGE_PASSWORD_SECRET=bridge-generated-password
```

From the application project directory, run:

```bash
python -m roboz.endpoints env encrypt
```

The command writes `.env.encrypt` beside the unchanged `.env` and asks for a
password. After verifying the encrypted file, remove or securely store the
plaintext source. Supply the password to `load_secrets` or set
`ROBOZ_ENV_PASSWORD` in the application's process environment. The loader
consumes that environment password only when it decrypts pending values.

```python
import os
from pathlib import Path

from pydantic import SecretStr

from roboz.endpoints import load_secrets
from roboz.shed.models import ActionVerdict
from roboz.shed.tools.email import get_work_with_email
from roboz.shed.tools.email.proton_bridge import (
    ProtonBridgeEmailService,
    ProtonBridgeSettings,
    ProtonBridgeTlsMode,
)

load_secrets()
service = ProtonBridgeEmailService(
    ProtonBridgeSettings(
        imap_host="127.0.0.1",
        imap_port=1143,
        tls_mode=ProtonBridgeTlsMode.STARTTLS,
        account_address="me@example.com",
        username=SecretStr(os.environ["PROTON_BRIDGE_USERNAME_SECRET"]),
        password=SecretStr(os.environ["PROTON_BRIDGE_PASSWORD_SECRET"]),
        certificate_sha256="<Bridge certificate SHA-256>",
    )
)
tools = get_work_with_email(
    service=service,
    base=Path.cwd(),
    default_verdict=ActionVerdict.deny,
)
```

The application owns the settings and passes the service to the tool factory.
Construction, tool binding, and dependency inspection do not contact Bridge.
Optional `signature=EmailSignature(...)` includes a caller-owned signature in
created drafts; omitting it creates unsigned drafts.

## TLS trust

Bridge commonly presents a local self-signed certificate. Supply exactly the
certificate's SHA-256 fingerprint in `certificate_sha256`, optionally separated
by colons, or supply a trusted `ca_file`. With neither option, normal system CA
validation applies. Both `starttls` and `ssl` modes are supported. The service
checks the certificate before it transmits credentials. A changed certificate
causes a failure until the application supplies the newly verified fingerprint.

For a local STARTTLS listener, obtain the fingerprint with:

```bash
openssl s_client -starttls imap -connect 127.0.0.1:1143 -showcerts </dev/null 2>/dev/null \
  | openssl x509 -outform DER 2>/dev/null \
  | sha256sum
```

Use the first output field. For `ssl` mode, omit `-starttls imap`. Adjust host
and port to match the configured listener. Never disable certificate checking
without a verified fingerprint.

## Operational checks

`service.check()` authenticates and discovers Drafts and Sent without changing
mail. A search does not mark messages read. Reading Inbox marks a successfully
read message as seen; reading Drafts or Sent does not. A source reference embeds
mailbox and UIDVALIDITY and becomes stale if that mailbox changes; search again
when a reference is rejected.

For a live smoke test, search a uniquely titled message, read it, and download
an attachment to an explicitly approved destination. Create a uniquely titled
draft addressed to yourself and verify it appears in Drafts without being
sent. Create a reply draft from the search reference and verify its recipients,
subject, and thread. After a draft timeout, inspect Drafts before retrying:
the server may have completed the append after the caller stopped waiting.

## Transport and operation boundaries

The provider uses IMAPClient 4.1 or newer. Tests or applications that inject a
transport use `client_factory(settings, ssl_context)`, returning an IMAPClient
with TLS already established. This replaces `imap_factory`; there is no alias.
The service verifies the configured fingerprint before login, uses UIDs and
timezone-aware reception dates, and closes each operation's connection.

Cancellation and timeout stop subsequent commands, including draft appends and
read-status changes. An IMAP command already in flight can still complete;
a cancelled or timed-out draft operation therefore requires checking Drafts
before retrying. The service never automatically retries an append.

`client_request_id` reuses a draft only when its stored header matches exactly.
This helps with retries but is not atomic: concurrent requests with the same ID
can both append a draft. References identify a mailbox, UIDVALIDITY, and UID;
mailbox names other than INBOX are case-sensitive. Provider failures propagate
instead of being reported as empty search results.
